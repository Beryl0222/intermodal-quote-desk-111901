# 联运报价邮件中的组合条件与可售方案

mail 的 replyTo 表示对某封邮件的回复。network 是服务路段及限界。requests 给出箱高和最大可接受无温控分钟数。allotments 是已收到的供应商包舱回执，编号在该供应商内唯一。transfers 用进出段编号表示可交接的路段组合。minutes 是换装耗时，conditioned 表示换装期间有温控。

资料保存在 `data/inputs.json`，采用 UTF-8 JSON。记录、人员、地点和业务编号均为合成内容。

运行环境为 Node.js 22.23.4，资料工具和测试使用 Node.js 标准库。

```sh
npm run inspect:data   # 读取资料并列出记录数
npm run workbench      # 渲染报价工作台（全部询价）
npm run workbench -- offers        # 有效报盘与改信修订
npm run workbench -- lock Q2 A     # 把方案 A 的确认容量锁给 Q2
npm run workbench -- present Q2 A  # 记录客户所看版本
npm run workbench -- revoke L1     # 撤销锁位（只释放本锁额度）
npm run workbench -- reset         # 清空本地锁位/出示记录
npm test
```

锁位与出示记录保存在本地 `workbench-state.json`（已 gitignore），可用 `--state` 换路径，`--data` 换资料。

## 引擎规则（src/）

- **parse.mjs**：邮件正文 → 结构化事实。中英文混排、无主题、无表格均可；每条事实保留原文片段供回查。识别价格（元/CNY）、直达与 via 经由路段、回执编号、选项引用（Option two / 方案二 / 前封第二种）、no split、分开下单、不含费项、冷车只到 X、全程冷接驳、另询、班次、路段限定词（东线车等）。
- **thread.mjs**：回复链 → 有效报盘。方案按线程登记编号；无新价格而带约束的邮件是改信，修订所指方案（E3 把方案二收窄为「冷车只到东库」）；同线程内路段与价格完全相同的邮件视为重复转寄，只算原来那次回执；指代不明的改信不擅自套用，只标记可能涉及的方案，完全不共享该条件或能力的其他线程报价不受影响。
- **plans.mjs**：路径枚举 → 报盘精确覆盖 → 校验。区间合价未说明可否拆卖时按不可拆处理；声明「分开下单」的报盘不得与所指方案同组；无温控分钟 = 无温控换装 + 明确无冷接驳路段的行驶分钟，超过询价上限即不可售；不相容的链路（缺换装资料、超限界、温控不达、货量不符）即使每段各自有效也判不可售；报价只字未提费项时标出费用口径缺口；货量与报价对象不符时金额不能沿用。
- **ledger.mjs**：包舱台账。同一包舱出现在多封邮件/多条路线描述里只算一份容量；只能锁有确切回执且余量足够的单位；撤销只释放本锁额度，不会把已给其他客户的额度加回。
- **workbench.mjs**：按询价组装对比视图——每段与全程的原文承诺、费用责任、剩余条件、当前已占容量；`present` 记录客户所看版本，改信到达后自动检出过时并列出差异（如「温控承诺 → 冷车只到东库」），需重报。

温控口径：只有邮件明确收窄（冷车只到 X）的路段才计无温控行驶分钟；换装分钟一律按 transfers 资料；「全程冷接驳」承诺会与换装资料交叉验证，冲突时列入待协调。
